## 二 最初审查为什么没有直接覆盖旧桌面端

早期问题包括：阶段之间格式不一致导致卡住、一键推进不能连续完成、反复修复消耗大量时间、人物资产提示词混入生产元数据、分镜创意与情绪表现反而变弱。用户目标是可靠批量执行且产出好看、有表现力的内容，而不是只有编译通过。

5c10d31 阶段分别形成了源码缺陷清单、第二阶段美术意见和 CLI/SDK 双入口方案。它们当时是建议文档，不能列成已完成代码。旧修复候选共 20 个文件，在 970c36f 中已有 10 个也被上游改动，直接复制会抹掉新增恢复与修订能力；因此改为按语义重新核对。

970c36f 已有视觉事实缓存和有界修订，但未加入本次人物美术与左肖像右三视图规范。第二阶段方案因此保留美术目标、重写接入点：把事实缓存和设计有效性分开；新美术上下文参与旧流程冻结和恢复；保护人工稿、旧图片和原任务身份。

到 2ac7c21，上游又补充范围化历史证据、对白遗漏的整编修订、经证明停止后的持久恢复及错误历史保留。这些进入实际迁移基线，不能继续当成未实现缺陷重新写一套。

## 三 独立项目的架构决定

用户决定新建 `K1rsam/director-desktop-next`，与原仓库分开。一套 Rust 业务核心、React 界面、规则和持久化契约同时服务 Windows 与 Mac。平台差异放在窄适配层，不维护两套各自改动的创作逻辑。

保留旧桌面端已有的 SQLite 工作流、缓存、原始回包、恢复、领域校验和四阶段界面；新应用使用独立应用标识 `app.director.next`、独立凭据命名空间和项目注册，不自动接管旧应用数据库、凭据或注册目录。

创作规则与工程合同分层：原版 3008 文件冻结，工程负责取料、身份、字段、执行、恢复和交付。Stage1/2 的人物、阶段资产、场景、道具应按当前集场与状态选择给 Stage3；不能把所有材料重复塞入，也不能借适配重写创作重点。

CLI 与 SDK 共享队列、任务身份、领域校验及修订预算。SDK 不天然获得更大额度或无限并行；未知任务不能通过换入口、重发或清空状态来“恢复”。

## 五 第二阶段到底改了什么

### 1 从“资料描述”转为“可见外观设计”

当前 M6.3 内的 `apps/desktop/rules/asset-art-director/SKILL.md` 是 M2 实施的 2.0.0 版，SHA-256 为 `9193cd59b44bdc77fb413fb8c40bb6531c2cfb9377ca17fafc0749808ba6cd82`。输出线协议仍是 `asset-design/v1`，便于保留既有身份与来源校验。

主要变化不是加一句通用“高级国漫”风格，而是要求把人物特征具体落实到协调的脸部比例、眉眼鼻唇组合、发型轮廓、肩腰衣长、衣料结构和主辅色。主配角及反派均可好看；差异化靠结构与整体造型，不靠丑化另一人或仅换瞳色、衣色。保留原文年龄、肤色、体型、疤痕和时代，美化不自动等于年轻白瘦或奢华。

集次、出处、剧情作用等留在结构化资料中，不整段抄入生图正文。但原文确有“第十集”招牌之类可见文字时不能机械删除。未来形象、角色自称和当前事实分开，派生状态只修改有依据的外形变化，保住基础身份。

### 2 默认角色资产图的展示

CH 基础与派生默认左侧大幅肖像/近景，右侧正面、侧面、背面完整全身，四处保持同一身份、发型、衣服和状态，头脚不截断，背景干净，无资料面板。GROUP、BEAST、LOC、PROP 不套 CH 模板。

### 3 美术设计有效性与恢复

新增 `asset-design-context/v2`，绑定实际技能哈希、原文哈希、资产与相关事实语义、合法直接来源链及来源设计哈希、有效风格、已确认方向、展示与画幅。其他人物仅作为美术对照，不成为当前人物事实或图片依赖。对照最多8条，每条正文1600 Unicode字符、序列化总计6400字符；当前人物必要事实不为对照让位而被截断。

## 六 第三阶段应怎样接入才不会再次改坏

### 已保全与尚欠缺

M6.3 的 `rules/stage3/manifest.json` 明确 `active:false`，状态为 `candidate_not_approved_for_runtime`。本包提供22份原版字节及哈希，不把顶层整合稿或三步实验设为生产基线。现有 `apps/desktop/rules` 中的桌面旧 Stage3 文件仍需历史回归，但不能冒称与 Mac 最新原版相同。

仅复制技能还不够。必须核对模型真正收到的 primary/methods、runtimeContract、Schema、读取范围、调用顺序、精修范围及最终采用逻辑。旧桌面端运行包装包含创作限制；若只替换文件而保留冲突包装，模型仍可能读到改坏的合同。

### 合并时必须保留的创作与生产关系

- 原剧本的对白、说者、声道、因果、身份和阶段状态是事实基线
- 情绪、表演、构图、运镜、幻想和声音协同创作；不能仅增加幻想标签，却削弱身体表现或摄影
- 幻想占用的时间在分组之前参与设计，避免最后硬塞超过单元上限；每单元上限30秒，通常尽量25至30秒，允许有意义的自然短尾
- 每个单元保留完整生产通用段，不因“去重复”删除用户生产所需内容
- 导演精修应真的诊断、局部改好并保住原强项；结果采用按实际链路验证，不能把任一原始精修回包直接等同最终采用稿
- Stage1/2 提供当前集场所需的角色阶段资产、道具、场景和必要历史，不要求 Stage3 重复生产已经存在的目录；不把晚期形象无条件当成当前身份

### 验收顺序

先锁定本机最终采用规则和必要运行源码的逐文件哈希，再实现适配与合成回归；随后用用户授权的同源剧本，应用内 CLI `gpt-6.1-sol / medium` 运行第1、2集，比较旧实际采用终稿。比较对白完整性、情绪落点、表演、幻想机制、摄影、时间容量、资产阶段准确性及整编前后保全。第一/二阶段可处理全剧必要材料，第三阶段不自动扩成全剧生成。

只有该证据成立，才能把“规则已归档”更新为“最新3008已接入并完成指定集验收”。SDK真实生成和第四阶段视频不属于本轮已经完成的测试。
