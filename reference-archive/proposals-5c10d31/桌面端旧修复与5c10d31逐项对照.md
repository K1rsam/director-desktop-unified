# 桌面端旧修复与当前版本对照

复核日期：2026 年 10 月 6 日  
当前版本：[5c10d315289862e8c452cb283e6df97616af57e5][current]  
旧修复起点：[280b5c4][baseline]，该 GitHub 提交不包含之后的全部云端补丁

## 结论

当前版本已有实质改善：新流程增加整数视频载体合同、定向有界修订、关联范围整编和完整单集发布。此前修过的部分原文解析、重复集确认和历史场次迁移问题，当前仍未看到等价处理；`unresolved` 完成门禁和全局目录冲突也仍待处理。因此应按当前实现补缺口，不能直接套回整份旧补丁。

这次严格区分三类历史：**以前实际修过**、**以前发现但未确认修复**、**以前测试过但不一定改过**。此前修复包目前无法读取，不能完成其与当前版本的逐字差异核对；以下依据历史修复记录、固定提交源码和本轮可执行检查作判断。“源码已有实现”不等于“本轮已跑通”。

## 一 以前实际修过的部分

### 相邻标题已处理  独立重复集确认仍缺

当前 v4 会把正文开始前相邻的同号标题归为同一个制作边界，见 [source.rs 657–682 行][adjacent]。这部分不能再简单列为“未修”。

但正文或场景隔开的真正重复集仍产生阻塞诊断，而保存结构只提供 `body/context` 范围决定，没有绑定精确标题 ID／坐标的重复集确认。界面也仅为两类局部范围诊断提供确认按钮；重复集进入警告列表。见 [诊断与决定结构][boundary-schema]、[决定类型校验][decision-kinds]、[SourceStructure 确认入口][source-ui]。

**最小复验：**相邻同号标题应合并；正文隔开的两个同号标题应能明确保留为两个制作段，确认后重开不丢身份。不要通过更改集号或把正文标成资料来绕过。

### 第 0 集现在是不同产品规则

v4 将所有第 0 集内容归为 `context`，即使标题是“序章”、包含场景或对白，也不建立正式制作集，见 [source.rs 668–673 行][zero]。原文仍保留，但是否参加逐集制作发生变化。

应先确定：第 0 集是否一律是辅助资料，还是允许作为需要制作的序章。本报告不将当前规则直接判为退化，也不建议未经确认恢复旧规则。

### 原文仍在  但部分分类会漏掉制作对白

- `1-1 日 内 大厅 甲：快走` 可以被识别为场景格式行。当前同行正文判断依赖动作标记等条件，随后只对 `body` 行提取对白，因此该句有进入原文却未进入制作对白清单的风险，见 [场景匹配][scene-match]、[行分类与对白提取][scene-dialogue]
- 将姓名整体转大写再判断 `OS/VO` 后缀，导致 `Carlos`→`Carl/OS`、`Bravo`→`Bra/VO`；显式 `小王os` 则是合法声道标记。历史修复记录确认曾处理“小写声道且不破坏 Carlos”的边界；Bravo 是本轮新增探针，不把它冒充为旧已修案例。需要同时保护姓名与合法声道标记，见 [parse_dialogue 483–524 行][voice]
- 场景标点仍有边界问题：`1-1 日，内，大厅` 不识别；`1.2 秒后 日 内 大厅` 可能误识别成格式行。`3.14元可以买什么`、`3-1日记原文` 则未命中，不能概括成“所有数字叙事都误判”。见 [场景正则][scene-regex]

这些结论包括源码分析和本轮 Python 规则探针，**不是 Rust 产品测试通过或原生界面复现**。优先补同行对白和姓名归属，再补标点与数字叙事边界。

### 手工场次排序与已有拆场迁移仍需补齐

手工决定将新场次直接追加进数组，之后按数组顺序建立 `sceneIds`，没有按原文坐标重新排序，见 [source.rs 1193–1231 行][scene-order]。最小用例是先确认靠后的片段，再确认靠前片段，目录仍应按原文顺序排列。

重新识别会新解析原文，再直接重放原 `scene_edits`；重放要求原 scene ID 与 episode ID 精确存在，见 [reparse_source][reparse]、[replay_scene_edits][scene-replay]。当相邻标题合并改变旧 episode ID 时，既有拆场及子场元数据可能无法继续重放。旧拆场迁移不能仅由“源文本哈希没变”证明安全。

另外，历史云端修复记录中的 v3 曾有相邻标题合并，而当前合并条件仅属于 v4；旧云端 v3 项目存在兼容风险。**这是历史行为和源码共同支持的推断，尚未读取旧修复包或真实旧 v3 项目复现，不能宣称所有旧项目都坏了。** 应先用真实或去敏后的已编辑旧项目验证，再决定迁移方案。

### 原有界面并发保护仍在

当前界面已有源版本／SHA 改变时关闭旧弹窗、请求携带 `expectedSourceVersion`，主界面也用 `busyRef` 阻止重复写操作，见 [SourceStructure 58–76 行][source-ui]、[App 76–91 行][app-guard]。因此不能把“独立重复集确认链缺失”扩大为“所有过期提交和重复点击保护失效”。

### Linux 凭据保护未保留为等价实现

当前锁定 keyring 3.6.3，但仅启用 Windows／Apple 原生功能；保存时临时创建 `Entry` 并直接调用 `set_password`，没有不支持平台的明确拒绝，见 [Cargo.toml][keyring-config]、[Cargo.lock][keyring-lock]、[settings.save][keyring-save]。

官方文档说明，无适用平台功能时使用 mock；mock 仅保存于该 Entry 内存，不提供持久化。因此当前 Linux 默认构建存在“保存调用成功却没有可靠持久保存”的风险。见 [keyring 平台功能说明][keyring-doc]、[mock 持久化边界][keyring-mock]。

这项只针对准备支持 Linux 凭据保存的版本，不代表 Windows Credential Manager 或 macOS Keychain 同样失效。本轮未在 Linux 产品中实际保存凭据。

## 二 以前发现的工作流问题

### 时长问题已补新流程  历史稿不能一概记为修好

新建 `storyboard.run` 会冻结整数视频载体合同，允许镜头和声窗有小数，但成品单元总时长必须符合视频能力。已接受稿不合适时，由原 Finisher 最多两次差量修订；无进展停止，整集发布前再校验。见 [新流程合同][carrier-profile]、[载体修订][carrier-repair]、[发布验收][episode-validation]。

数值累加误差使用 1e-6 容差，真实 14.5 秒不会被自动取整，见 [binding.rs 7–13 行][duration-tolerance]。旧无 creative profile 快照仍走兼容路径，已有测试还允许 4.5 秒旧稿通过领域验证、同时标为需要修订，见 [旧 profile 处理][legacy-profile]、[小数时长测试][duration-tests]。

**最小复验：**新旧 profile 各测 14.5 秒、浮点累加误差、模型允许时长列表、修订无进展、两次失败；确认未裁声窗、未重跑已付主创，旧稿不能被误称可直接生产。

### 单次失败已改成定向有界修复

`call_validated` 本身仍为一次执行、失败后拒绝并返回，见 [pipeline/mod.rs 240–272 行][call-validated]。新修复在上层针对资产适用范围和视频载体等明确问题分流，保留原错误稿为未采用状态；修订后重新执行完整领域校验。

持久化执行器会回读绑定 workflow、节点、请求哈希、原包及接收事件的结果，未决修订占用原预算，不因恢复再发同一节点。见 [有界修复分类][repair-kinds]、[原结果回放][repair-replay]、[未决预算保护][repair-budget]。

这是部分问题已有修复，不是任意错误都能自动修。来源、身份、原话等硬错误仍须拒绝；不宜机械加一个通用重试循环。

### unresolved 仍不影响完成与逐集发布

当前 `complete` 只检查 `localBlocked`，随后把含 `unresolved` 的结果送入完整集发布；最终 `completed` 也只看 waiting／blocked。发布验收没有检查 `unresolved`。见 [完成判断与发布][complete-check]、[最终状态][completed-status]、[发布验收][episode-validation]。局部重做也有同样边界，见 [局部结果状态][partial-status]。

**建议优先处理。** 给一份其他字段完全合法的稿件加入明确阻塞的 unresolved，验证它不能仍发布为完成稿。如果希望允许建议项，需先区分建议与阻塞问题，不能默认全部忽略。

### 全局资产守卫仍会拦住无关编辑

版本守卫记录全部活跃资产，检查全局 foundation 版本、每个资产版本和目录总数。另一集的不相关资产增删或改版也可能拦住本集发布。见 [guard_from_input 与 verify_guard][global-guard]。

它仍能防止覆盖并发修改，问题在于范围过粗。最小复验需同时覆盖“改无关资产不应阻塞”和“改真实依赖必须拒绝”，不能直接删除守卫。

### 整编与发布已有实质变化  创意质量仍要单独验收

旧版每个主创批次之后立即整编；当前先保留相关已接受主创稿，再按完整请求容量尽量合并连续范围进行整编，超容量仍可能分组。见 [关联范围整编][related-finish]。

完整单集通过后可在整个流程运行中原子发布，后集失败不应抹掉前集，重放应幂等。见 [发布事务入口][episode-publish]。已有测试包含“两个 5+3 行主创批次合成一次 8 行整编”和“已发布集在重开、后集失败后保留”，见 [合并范围测试][related-finish-test]、[逐集发布测试][episode-publish-test]。

这些是执行和完整性保障，不证明长集全局节奏、情绪、表演与画面质量已经合格。

## 三 以前测试过的能力不能全部算作新修复

直接对照 GitHub 280b5c4 原始源码，`tasks.rs`、`media_probe.rs` 和 `video_preflight.rs` 测试在忽略文件末尾空白后与当前相同。原任务 ID 查询／下载恢复、未知提交不重发、媒体探测等核心保障主要是保留既有实现。

- 恢复必须使用已保存任务 ID；下载验证返回身份，导入后关联媒体。见 [tasks.rs][tasks]
- 查询和下载重试各自有预算，不能自动重试生成；重启保持已知 ID 和未知提交状态。见 [恢复与重试][recovery]
- INLINE 父图、AUDIO、文字素材及语义版本绑定有新增覆盖，见 [素材绑定测试][binding-tests]
- scheduler 新增防止旧生成积压饿死原任务下载、公平分配、未知提交与退避保持；80 集重启零重发用例仍在。见 [调度测试][scheduler-tests]
- 视频采用仍需可信运动视频元数据、媒体哈希和当前单元版本；下载不等于人工采用。见 [视频采用检查][adopt-video]

以上当前 Rust 测试均只核查了源码与断言，本轮未执行。真实渠道故障恢复与人工画面声音验收仍需分别记录。

## 五 建议的最小处理顺序

1. **先保护制作含义：**同行场景对白、Carlos／Bravo 姓名、独立重复集确认，以及 unresolved 阻塞完成门禁
2. **先验证已有项目再迁移：**旧 v1/v2/v3 项目、相邻标题、已拆场和子场元数据；核对原文／哈希／UTF-16／集场身份，并重开及导出再导入。第 0 集规则先作产品决定
3. **复跑当前新实现：**整数载体修订、资产范围修订、两次预算、无进展停止、收到原包后中断、未收到原包后中断、恢复零新增调用、完整集幂等发布
4. **按目标平台补安全边界：**Linux 若要支持凭据保存，应先明确安全存储方案或拒绝不支持的保存；Windows／Mac 分别验收其原生实现
5. **再处理局部隔离与体验：**无关资产编辑冲突、手工场次排序、场景标点和数字叙事边界；最后分别做模拟渠道全链路、真实渠道恢复与人工创作品质验收

本报告仅给出对照与复验建议，没有修改产品代码、迁移项目或发布客户端。
