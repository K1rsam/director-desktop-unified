## 3 先修单资产设计的新身份不一致

这是源码调用链发现的高优先级风险，**尚未用 Rust 或原生客户端复现**，不要写成已发生的用户数据事故。

### 问题定位

`images.design`／`images.produce` 使用 `workflow_id: None` 的 `SavedTextExecutor`。新的 `accept` 和 `reject` 都先调用 `standalone_asset_received`，其 `standalone_identity_matches` 要求 Codex `executorIdentity` 正好含三个字段，并有匹配的 `version`。

但当前 `request_snapshot` 默认只记录 `provider` 和 `executable`。只有 Windows 的应用托管目录命中新预检分支时，才把身份替换为包含版本的 `inspected_cli_identity`；`managed_codex_root()` 在非 Windows 返回 `None`。因此非托管原生路径的新任务可能已经生成并保存原回包，却在采用／拒绝回调时被挡为 `CODEX_STANDALONE_ATTEMPT_UNRESOLVED`。现有独立恢复 fixture 手工构造了三字段身份，不能证明真实新任务路径正确。

证据：[新任务预检][identity-dispatch]、[请求与恢复身份要求][identity-match]、[采用回调][identity-accept]、[非 Windows 托管根][managed-root]、[第二阶段执行入口][image-exec]。

### 修改要求

1. 先写经过真实生产构造路径的离线测试：新建请求 → 预检 → 持久化任务与请求哈希 → 模拟原回包事件 → 领域校验 → `accept`／`reject`。不要只手工插入一个理想的数据库快照
2. 为新 Codex 请求建立一致的、经实际预检确认的冻结身份，覆盖 Windows 托管目录、Windows 显式原生路径及 macOS/Linux 原生路径。保存的版本必须来自本次已验证执行文件，不得从另一安装或可变设置拼接
3. `execute`、`result_snapshot`、回调和恢复读取同一份冻结身份。身份加入哈希前后，不能失去已存在未决任务的所有权检查
4. 旧两字段记录单独处理。能证明原请求、执行器身份、原回包事件、哈希及状态一致时，才走有审计的兼容路径；证据不足就保留并报出阻塞。不能批量给旧记录补上“当前版本”，也不能因为恢复失败而重发
5. 保留新版 Windows 托管安装迁移的严格证明。不要为修复本项直接放宽 `object.len()==3` 或所有路径检查，更不能用更换 `node_key` 绕过旧任务
6. 文本 API provider 保持独立身份合同，不被误送入 Codex 专属恢复逻辑

### 必测

- 新任务有效采用、领域拒绝、接收后中断、重启后采用、重复回调幂等
- 两字段历史记录、三字段记录、版本不符、执行文件不符、原事件不符、两个未决任务、缺失原包
- 所有失败分支保留原证据；恢复时生成调用计数为零

## 4 原文解析与项目迁移

### 4.1 保留新版系统播报修正

`system_message_segments` 只把说者为系统／系统音、声道为 VO／系统音、整段被一对 `【】` 包裹且原先无发声段的特定情形转成发声段。它保留原字符、括号与绝对 UTF-16 区间。`validate_integrity` 只兼容能够从锁定原文精确重建的旧分段，篡改区间仍被拒绝。

新增解析规则与旧项目升级都必须保留这条路径。不要将旧冻结 `source.rs` 整体盖回去，也不要把所有括号内容普遍变成台词。[播报分段实现][system-wrapper-function]、[旧分段验证][system-wrapper]

### 4.2 为新识别规则建立独立版本

旧冻结候选使用 `source-parser/v5`。实施时先确认新版没有其它分支占用该版本；本基线仍为 v1–v4。若使用 v5，就让新导入和用户明确重新识别进入 v5，已有 v1–v4 继续按原规则校验。新版系统播报的已定义兼容例外必须保留，不能借升级机会广泛重解释已有项目。

具体修正：

- `Carlos`、`Bravo`、含非 ASCII 拉丁字符的姓名不因不分隔的 `os/vo` 结尾被截断；中文姓名后明确附着的 `os/vo` 继续支持。拉丁姓名使用空格／括号等明确标记时仍可表达声道
- `1-1 日 内 大厅 甲：快走` 等同行对白，在原行中提取精确说者与引用范围；同时保留场景身份。不要删去场头再重构原文，不把字节下标当 UTF-16 下标

- 无法唯一确定的多说者或场景负载保留诊断，不用自动猜测清除阻塞
- 手工场次决定完成后按原文位置重建目录和成员顺序，保证先确认后段、再确认前段仍顺序正确

当前未修依据：[声道后缀][voice-suffix]、[同行分类][inline-source]、[决定与目录重建][boundary-decisions]。

### 4.3 独立重复集需要专门确认

## 5 第二阶段设计与图片请求

本节是整合要求；详细提示词、字段和验收见同次交付的 `stage2-asset-system-prompt-change-proposal-970c36f.md`。以下关键边界即使单独使用本文件也必须执行。

### 5.1 修改目标

`asset-art-director` 当前仍为 v1.3.0，新提交没有加入画风输入、人物差异对照或四视图展示编译。

- 把第一阶段事实和状态差异转换成简洁、可画出的外观描述；集场编号、来源编号、剧情解释留在结构化证据，不复制到生图正文。原文明示的招牌、衣服字样等可见文字除外
- 以项目当前画风设计；统一画风不等于同一脸型、体态、肤色。人物以骨相、眉眼、发型轮廓、体态、衣装等有用特征形成差异，不按正反派标签决定美丑
- 大多数人物应好看、有吸引力，主角、配角、正派和反派均可俊美；通过结构与气质区分人物，保留原文支持的年龄、肤色、体型、伤痕等身份特征，不靠丑化制造辨识度
- 变体遵循原身份，只改有依据的状态或外观部位；跨角色设计对照不是新的剧情事实，也不是图片依赖
- 新 AI 人物设计的默认最终展示采用左侧肖像、右侧正／侧／背完整全身；用户明确的构图优先，已选比例优先，缺失时才用默认 16:9
- 手工正文和无法可靠识别来源的旧稿保留原构图，不偷偷重写。不要增加未经要求的 BJD 预设或强改项目风格
- UI 明确复制的是设计正文；实际提交由程序编译公共画风和展示要求，避免模型与程序重复堆叠

### 5.2 接入与缓存

新增领域输入可以沿用旧候选中的 `projectVisualStyle`、`imagePresentation`、`comparisonDesigns`，不要把完整设置或凭据传给模型。

人物对照按稳定资产身份排序去重，排除自己、来源链、删除项、其它类型和过期 AI 设计。可先采用最多 8 项、每项 1600 字符、合计 6400 字符作为工程起始预算，并通过容量、边界和质量测试调整；这些数值不是用户指定的固定合同。不得截断第一阶段的原文证据、必需事实或规则正文来满足对照预算。冻结本次实际使用的对照内容，不能恢复时换成最新目录重建同一个请求。

新 AI 设计的有效性应绑定美术规则内容摘要、项目画风、展示上下文及当前资产和合法直接／来源依赖链的语义版本。`comparisonDesigns` 只是冻结的可追溯设计上下文，不新增资产依赖或全局失效边；另一人物以后改稿，不能据此使本人物或全项目自动失效、重新设计。手工稿、历史图、已提交任务不因版本更新自动失效并重生成。需要新设计时只在用户明确的设计／制作操作内执行。

### 5.3 必须保留新版事实检查与恢复

新版 `asset_visual_facts` 增加状态归属检查、有界修订、精确缓存证明；其 `ruleSha` 对应事实提取规则，不能复用为 `asset-art-director` 设计有效性。两个层次分别验证和失效。

新版 `run_asset_design`／`images.produce` 已接事实 gate；`images.run` 当前直接进 `queue_images`。实施时同时覆盖“直接生成图片”和“一键制作”，确保不因入口不同绕过必需事实约束，且检查本身不擅自重写手工正文。不能泛称所有图片入口目前都已受 gate 保护。

新版 `imageResumeOrigin` 的旧请求与旧 settings 恢复必须保留。新增设计／对照／展示字段要进入同一恢复合同。`queue_images` 仍会读取当前 `store.settings()`，因此要单独证明恢复后的最终图片 prompt、画风、比例、尺寸、渠道、模型、有序引用和设计版本来自正确冻结输入；不要因上游有旧 settings 就宣称最终图片请求已经全部冻结。

新设计上下文与旧接收原包冲突时，不得把旧回包重新盖成新上下文已接受，也不得为了继续制作自动再发一次模型。先保留旧任务证据，再提供明确的可继续状态或阻塞原因。

主要入口：[资产设计管线][asset-pipeline]、[图片执行与恢复][image-engine]。

## 6 补齐 unresolved 完成与发布门禁

当前整集只根据 `localBlocked` 判断可发布，最终状态仅看 waiting／blocked；局部重做也只根据 blocked 决定 completed。`validate_episode_delivery` 尚未拒绝非空 `unresolved`。[整集完成][complete-gate]、[逐集验收][delivery-gate]、[局部采用][partial-gate]

当前契约只有 `{coordinate, problem}`，未区分建议与阻塞，因此本次把任何非空 `unresolved` 视为未完成。不要擅自把字段清空、降级为日志或引入未经产品确认的“建议项”类型。

修改要求：

1. 整集保留合法草稿、修订记录与 unresolved，但不发布为完成集，不加入完成集列表，不推进后续依赖的已接受边界
2. 依赖未解决集的连续后集等待处理；此前已发布集不回滚
3. 局部重做有 unresolved 时保留候选，不替换原单元，不更新采用边界、不退役旧单元
4. 单集发布、最终发布和存储事务入口重复验证，拒绝上层伪造 completed 或清空 blocked 的绕过
5. 读取缓存和恢复仍保留 unresolved，不能因恢复把预算重置后自动追加调用
6. 与新版 `author_chain_revision`／continuity 分支协同：只有真正接受且满足发布条件的上游状态才成为新依赖，不能传播未采用候选的尾状态

不要取消新版针对已知局部资产范围、同集场号或来源覆盖问题的原整编岗有界修订，也不要退回“所有来源相关校验错误都直接拒绝”的粗规则。只有明确列出的可修问题进入原岗修订；跨源污染、缺失证明、改写原话等不受支持的错误仍应拒绝。修订结果照样通过完整校验和 unresolved 门禁。

必测：整集有 unresolved、局部有 unresolved、缓存回放有 unresolved、伪造 completed、已发布前集＋失败后集、旧单元不被替换、后继依赖不推进、重复发布幂等、无新增自动生成。

## 7 凭据与发布守卫

### 7.1 不支持平台的凭据保存

当前 keyring 只配置 Windows／Apple native，`settings.save` 仍直接 `Entry::set_password`。旧冻结的 Linux 非持久存储拒绝逻辑尚未进入新版。[依赖][keyring-cargo]、[设置保存][keyring-save]

在写入任一非空 BH／Chrome／文本 API 密钥之前统一验证持久化能力。不支持时整个设置保存操作失败，普通设置也不先部分提交，错误不含密钥。全为空的凭据字段不能阻止纯普通设置保存。Windows Credential Manager 与 macOS Keychain 路径保持，分别验收。不要为本项临时启用未设计的 Linux 凭据后端或落盘明文。

### 7.2 保留审计专用放行 不扩大成通用忽略

新版 `refresh_storyboard_audit_guard` 只在扣除 `version`、`visualFactBatches` 后 foundation 内容完全相同、源一致、其它守卫全部通过时重绑定发布依据，并保存证明。这解决的是审计更新造成的特定冲突。[审计守卫][audit-guard]

`verify_guard` 仍检查全资产版本和资产总数，所以无关资产编辑仍可能阻断发布。[全局守卫][global-guard]

本轮先保留此限制。不能直接删除资产数、版本或 foundation 检查。如果后续单独实施范围缩小，必须先冻结并证明完整真实依赖闭包，再同时验证“无关编辑不拦”和“实际依赖变化必拦”；不得把本次审计放行推广到新的设计上下文、画风或目录变化。

## 8 新版恢复能力的保留清单

整合任何旧修复时，以下是不可退回的验收条件：

- 受支持的已接收回包必须绑定原 workflow／节点／请求快照哈希／raw event／回执，域校验通过才采用；证据不足保留未决状态
- 修订预算保存在原任务链中；进程重启、新图片流程外壳或重新选择设置不增加原预算
- Windows 托管 Codex 路径升级不等于换一份生成任务；显式自选路径仍权威，不能静默改道
- 原主创修订后，只对实际依赖已改变的同集后续主创及相关整编建立有证明的新分支；健康缓存复用，旧分支及错误留存
- 新版共享原行传输必须可逆，展开后等于完整领域输入；保留 UTF-16/Unicode 与受保护字段。容量按实际 dispatch 包装计量，不能只量 input 或截断规则、原文、现稿
- 视频 `autoSubmit:false` 只是准备任务可以批量处理，不等于授权付费提交；不能为提速放宽未知提交或生成所有权
- 图片／视频查询、下载继续使用原任务 ID；重启不重发，下载完成不代替可信媒体探测和需要的采用校验

具体修改点与必保留测试：

1. `saved_author_chain_revision` 只允许 `acceptedContinuity`、`plan.acceptedContinuity`、`plan.dependencyExits`、`dependencyOutputs` 四处依赖变化，而且必须有同 workflow、同集、真正已采用整编的原包和回执证明。源、素材、规则、模型、schema 变化不能借这条分支豁免。测试相同输入零新分支、合法变化仅新建受影响分支、伪造／跨集证明拒绝、后续整编继承分支。[主创依赖证明][author-proof]
2. 同岗修订最多两次，问题无进展或出现不受支持的硬错误就停。A15 事实修订在新的图片 continuation workflow 中仍使用原 source packet／原请求／raw／attempt 预算；不能因为外层 workflow 换 ID 而再获得两次。[原岗修订][bounded-repair]、[A15 回放][a15-replay]
3. `compile_storyboard_dispatch_transport` 的发送压缩与历史 Finish grouping 分开保留：压缩省空间不能重组已冻结作者范围。对中文、emoji、重复行、所有 source refs 和受保护原稿执行完整展开相等测试。[传输编译][transport]、[整编分组][finish-grouping]
4. 视频新增准备 burst 是每渠道最多 64 项、逐项间两秒软预算。`prepare_only` 结构上不得调用 submit；准备期间设置改成 autoSubmit=true 也不应把这次准备变成付费发单。同时回归已知任务 ID 的查询公平性、shutdown、损坏 prepared／receipt、磁盘失败和其它健康任务继续推进。[准备专用路径][prepare-only]、[调度 burst][prepare-burst]

两秒是逐项检查的软预算，不是单次渠道调用的硬超时；不要据此对界面承诺整批在两秒内完成。

## 9 CLI 与官方 SDK 双入口方案的兼容修订

这部分只更新既有方案的工程前提，**不在本次补丁中实施 SDK、安装运行时或换掉 CLI**。CLI 保留，SDK 后续另获实施授权，工作流的 backend 一旦创建就冻结。

既有双入口方案需要补充以下内容，不能直接照 5c10d31 的接口清单实施：

1. `TextExecutor` 新增 `input_transport_characters`、`visual_fact_repair_context`、`author_chain_revision`。SDK adapter、包装器、fake executor 必须逐项实现或明确转发；继承默认 `None` 不能算功能兼容。[接口][executor-hooks]
2. 容量门禁跟随实际 backend 的最终 dispatch 封装计量，并保留新版历史整编分组兼容，避免升级 transport 后重组已冻结的整编范围
3. 新版主创依赖证明部分依赖 managed CLI 原回执。SDK 要建立带版本、区分 backend 的持久证明；不能伪装为 CLI 的 `executorIdentity`，也不能往现有严格三字段身份里随意塞 SDK 字段
4. SDK 与 CLI 的请求、回包、取消、未知提交、修订、缓存与发布合同应在领域层相同，但原运行时路径、版本、会话／轮次标识属于各自冻结身份。切换设置不迁移正在运行或未决的旧 workflow
5. 把第 3 节非托管路径的新任务身份用例加入 SDK 前置门槛。先保证现有 CLI 各路径的 execute→raw→accept/reject 链完整，再对两种 backend 做同等故障注入
6. 增加图片恢复、A15 事实修订预算、接收后中断、修订后后续主创分支、unresolved、可逆原行 transport 的双 backend 等价测试
7. 新版没有实现官方 SDK 生成通道，也没有增加文本模型并发。调度优化不要被写成“已经支持多路文本生成”或“SDK 可自动并行完成 80 集”

官方 SDK 具体版本、平台支持、打包和协议限制，应在真正实施时按所选锁定版本重新核实。本文件只核对本次仓库变化，不更新或背书先前方案中的外部产品时效性结论。
