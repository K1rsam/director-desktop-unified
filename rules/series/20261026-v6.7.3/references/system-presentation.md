# 剧情系统的呈现选择

源中出现任务、奖励、提示、数值等剧情“系统”时读取本合同。这里处理观众看到、听到它的方式，不改造源世界规则；没有系统的剧本不强行增加。先通读其实际出场及揭示，区分原文明示与仍待决定的部分，再判断是否需要提问。

## 原文已明确时直接沿用并说明

先按系统身份及实际生效集场核原文。原文已明确面板、化身、混合等呈现方式时，主控直接沿用，在用户可见的执行消息里简短说清“本次采用什么、源依据在哪里、何时适用、可见/可听范围的已知边界”，让用户看到实际处理结果；不能只藏在工作文件、默认包或子代理回执里，再让用户追问。

原文例如已写金色光幕和界面里的卡通脸，就明确告知沿用这两种表现及各自作用，不为同一设定再弹面板/精灵选择题。只陈述有依据的内容，外观不自动证明它有独立身体、能被旁人看见或改变原声道。采用依据记录为“原文明示，直接沿用”，保留源坐标、出现时点及适用范围，不伪记成用户逐项确认。

只有未明示的表达事项会影响实际制作、原文有实质冲突，或用户明确要求改变源呈现时，才就该范围并入既有集中确认；已明确部分继续保留。仅出现“系统”“叮”或系统音，不足以证明视觉形态已经明确。普通配色、材质等细节按已定美术方向完成，不因有多种设计可能就新增确认。

用户只问“现在系统是什么形式”时，直接解释当前采用、依据和边界；这不等于要求改选。已有有效制作决定直接继承；其与原文明示冲突时明确指出，只问真实冲突。修订仅影响用户明确生效范围，不重开无关决定。

## 需要选择时再展示方案

沿源索引分别标识每个系统的稳定身份、别名、提示/原声来源与适用集场。多个系统不共用一个模糊的“系统”决定；同一系统的面板与精灵外观也不自动拆成两个叙事身份。原文只写脑内提示时如实记载，不能推断已经有面板或实体。

向用户展示候选时，不只列模式名称。每项用一两句说明本剧里如何出现、怎样承载原有提示、和主角如何形成观看/反应关系，并说明选择理由及限制；用同一处真实源提示作对比，原话不改。下面是可组合的创作菜单，不是红果平台的统一规范或流行度排序：

| 方案 | 用户能理解的效果 | 必须说明的区别 |
| --- | --- | --- |
| 信息面板 / HUD | 提示在主角视线附近展开，当前有效信息随源事件出现、更新或收起；材质可随项目采用科技屏、符箓卷轴等 | 是世界内载体、主角私有界面，还是只给观众看的图形；不能编造数值、任务或未来奖励 |
| 小精灵 / 角色化身 | 让系统有稳定轮廓和性格化反应，例如在提示出现时探头、悬停或显出态度 | 是源实体、意识内化身还是观众用的视觉拟人；不因此获得身体、能力、关系或新对白 |
| 纯声音 / 无新增可视载体 | 保留原提示音，用主角眼神、动作停点和声音位置呈现接收过程 | 仅谁能听见按源；不为声音强配人物图，也不凭此删除源已有的屏幕/实体 |
| 符号 / 道具 / 环境化 | 以选定的光纹、器物界面或局部环境变化承载原有提示，形成符合题材的脑洞表达 | 提示视觉化与剧情中的真实变物分开；不能新增可触碰道具、改变环境结果或让旁人因此知情 |
| 混合模式 | 日常提示用声音或简洁界面，需要解释或情绪互动时出现已选化身 | 明确各形态的触发、可见域和切换规则；不能每集换脸，也不能把“混合”当无限增添表现的许可 |
| 保持原文 / 自定义 | 沿用源已有表现，或采用用户明确描述的方案 | “按原文”仍需记录已有载体与声音；自定义同样核身份、权限和连续性 |

确需选择时，根据完整源文提出最适合的推荐及有区别的替代方案，说明其余菜单可选。源已锁定的实体、外观或呈现方式列为沿用说明，不把互斥改编伪装成普通选项；源内普通设计差异由既定美术方向处理。不同系统分别判断是否需选，也可在用户明确同意时共用规则。用户说“红果感”时转成可讨论的造型、信息密度、节奏、趣味与声画做法；提具体作品须有可回查证据，搜索摘要不冒充看过画面，未核实则标创作提案。

## 保存真实决定与边界

复用 `decisions/expression.md` 或现有方向文件；需要精确投影时可另存 `decisions/system-presentation_vN.json`。这属于工作资料，不是新增 bundle 原生字段或自动校验协议。每个系统至少保留：

- 稳定身份、源锚及适用集场；源明确的外形/能力/声音/文字及时点，未知仍记未知。
- 展示过的方案、推荐理由、实际所选模式与具体外观/出现规则；候选、已选、待决定、取消状态分开。
- 实际采用依据：原文明示沿用、用户选择或既有明确委托；版本及生效范围分别记录。原文已明确且无真实冲突的部分不记为待用户选择；未决定只阻塞真实依赖，不伪记已确认，不逐集重问。
- 谁可见、谁可听、是否可触碰；分别记源事实和制作选择。观众可见不等于主角可见，更不等于其他角色可见。
- 相关设计 ID/版本或“无独立视觉资产”、源原声/文字处理与旧决定被替代的范围。

系统原有身份、原声、必要提示和源载体不因额外幻想 `off` 或叠字关闭而消失。系统呈现决定只授权其中明确的视觉化，不顺带授权额外幻想、编辑字卡、对白字幕、新提示或新能力；已有“不得新增可视载体”等明确限制优先。若所选方案与有效幻想/呈现限制实质冲突，在集中确认中指出并只问该冲突，不能静默改开关。原文已明确精灵实体、固定外观或只有某人可见，不能凭推荐面板/纯声模式抹去。

**声道不随外观自动改变。** 源为系统音时保留系统音/允许的画外呈现；显示小精灵不等于授权把系统音改成画内嘴部对白或为它添台词。源确为角色现场对白时按实际源声道处理。按[数据合同](data-contract.md)保留原说者、逐字文本、声窗及 voiceBindings 规则，不能为了可见化身强加系统音人物声源绑定。

## 从选择进入设计和实际镜头

1. **设计**：反复可见的面板/化身先完成 `design.full`、核源采用与 `design.text`；决定给出需要的配色、轮廓、信息布局、尺度与出现规则，完整设计落实。身份、呈现载体和导出类型分别记录；面板通常按 PROP，化身依实际设计登记，不据 CH 后缀把它变成世界内人物。纯声源不建虚构图片，临时正文表现可无独立卡。
2. **供料**：使用现有 `context_packet.py`，将本集相关系统的同版决定放入 `kind:"direction"`，保留原文件 hash；资产放 `assets`，当前可见/知情状态放 `state`。精确选 JSON 子树时保留该系统完整有效决定，不能只传 `mode`。系统未出现的集不灌入无关长表。主创、整编和独审都读同版相关决定。packet校验不判断决定是否适用于当前集，主控与接任者须逐系统核生效范围；旧版本字节完好不能代替本集有效版本。
3. **落实**：把采用方案写到实际 `picture`、`unitDirection`、声音和初末态；明确出现、提示、主角反应与退出/延续。纯旁观图形/主观化身不混入现实 `participants`，主观主体按现有 `visualSubjects/visualSubjectBindings` 处理；是否纳入 `imageBindings` 取决于实际参考图片用途。面板内容依源和字卡许可写准确文字及可读位置、大小、入驻退；决定文件或标签不会自动导出这些画面。
4. **复核**：逐系统对照源、有效决定、当前完整设计与实际镜头，核形态一致、可见/可听/接触、源原声与文字、时点和他人反应。尤其查声音变嘴部对白、私有面板被旁人读取、模式已选却正文仍套旧面板、双系统串用设计。工具仅核其已实现的结构和字节，语义仍须读稿。

## 改选、分批与交接

用户改选或在既有委托内修订时先另存候选决定和真实生效范围，核受影响设计及消费者，再建立新版设计、供料和完整稿候选；核验后采用。已完成集/旧已采用稿不因全局文件变动被静默覆盖。涉及旧稿返修时明确范围，失败保留原采用；只更新真正依赖该决定的集/包，不重做另一系统或无关集。

本地没有3008的已付请求/执行批次manifest。多工作包与上下文轮换沿[版本化补漏步骤](production-contract.md#额外幻想补漏的本地执行)：停止受影响旧写者、保存原采用与领取依据，在新版决定/计划/选择/资产/packet下续接；不改旧包的hash冒充它已读新决定。分批不是取消已授权补漏的理由，也不是放宽选择许可的理由；整集装配与独审对照同一有效版本，采用稿换版后回读工具标出的下游旧绑定；即使出口兼容，旧hash绑定也可能成为STALE，应据实reconcile，真实有影响才局部改稿。字段/流程通过不等于真实模型或视频效果已验证。
